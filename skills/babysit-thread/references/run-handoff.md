# Check the return path after a T3 launch or resume

1. Re-read T3. Record the link, scope, expected handoff, environment and thread IDs, and exact active or queued run ID. Check pending questions, approvals and awaited work. If a run already ended, inspect its latest state and handoff now. Follow an active replacement only when it continues the same scope.
2. Confirm one way the exact run can return to the owning conversation. Reuse the owner's confirmed handoff if it covers this run. In T3, prefer `thread_wait` with `environmentId`, `threadId` and `runId`. Include `untilDelegatedWorkSettled: true` when needed. Treat `next` as a wake only if it explicitly confirms the owning conversation will resume, including when `timedOut` is true. Outside T3, use a supported one-shot route. Record the accepted wait or callback and which conversation it will resume.
3. If no return path is confirmed, use one bounded `thread_wait` if available and you have not made one for this run. Re-read T3. If still active, use one permitted follow-up with the exact IDs. If none is available, give the requester the thread link, active run and last verified status, and say automatic follow-up is unavailable. Leave active, blocked or approval-pending work open. Avoid recurring checks and parallel watchers.
4. When notified, verify the signal names the watched run and re-read both the watched and latest runs. Check pending questions and approvals, and verify required reviews and evidence from the recorded parent and awaited child handoffs. If this is an active same-scope replacement, verify the old route ended and repeat this checklist for the exact new run. If the scope changed, return ownership to the requester. Report completion after verifying the brief and its evidence.
